# MIGRATION_CHECKLIST.md — データ層移行時の消費者横展開チェックリスト

作成日: 2026-07-30
出発点: `[[TTM-PASCALCASE-KEY-STALE-1]]`（`BACKLOG_DONE.md`参照）。
`common/sec_data`統合フェーズCで`ttm_series.json`のキー命名規則を
PascalCase→snake_caseへ移行した際、全消費者への横展開確認が行われず、
`data_fetcher.py`（RICEスコア・FCFソース選択）・`audit.py`が旧キー参照の
まま取り残され、最大3〜4日間の本番影響（RICEスコア全100銘柄停止・
FCFソース94銘柄誤動作）が発生した実例を踏まえて作成する。

## 本ドキュメントの位置づけ

- **本ドキュメント**: 「どうすれば同種の見落としを防げるか」という**手順**を記録する。
- `BACKLOG.md`/`BACKLOG_DONE.md`: 個別の課題・完了記録（「何が起きたか」）。
- `SEC_EDGAR_LAYER_DESIGN.md`: SEC EDGARレイヤー統合固有の設計判断（「なぜこの設計にしたか」）。

3者は役割が異なるため、本ドキュメントは独立ファイルとして扱い、上記2ファイルの
既存記述は変更しない。

## 対象とする移行

出力データの**キー名・スキーマ・フォーマットが変わり、かつ複数の独立した
消費者（読み手）が存在する**移行全般。特に以下のような、単一のコミットで
生成側（producer）だけを変更しても、消費側（consumer）が別ファイル・
別モジュール・別チーム相当の管理下にあるため追従漏れが起きやすいケース。

- `common/sec_data`内の既存移行（フェーズB・C等）の残タスク
- `PROJECT_STATUS.md`フェーズ1に記載の`common/market_data/`新設（yfinance統合層）
- `PROJECT_STATUS.md`フェーズ1に記載の`common/macro_data/`新設（FRED統合層）
- その他、`docs/architecture/new_data_platform/`配下の設計に基づく新規データ層構築全般

## チェックリスト

### Step 1: 移行前 — 全消費者の洗い出し

キー命名規則・スキーマ変更を伴う移行に着手する**前**に、対象キー名を参照している
全ファイル・全関数をgrep等で洗い出し、リスト化する。

```bash
# 例: ttm_series.jsonのflowキー"OCF"を参照している箇所を洗い出す
grep -rn '"OCF"' --include="*.py" .
grep -rn "flow\.get(" --include="*.py" .
```

洗い出したリストは、影響範囲・修正の緊急度を判断できるよう以下3categoryに分けて記録する:

| 区分 | 該当例 | 見落とし時の実害 |
|---|---|---|
| **本番消費者** | `pipeline.py`・`reader.py`・`data_fetcher.py`等、実際の計算結果・レポート出力に反映される経路 | サイレントな計算誤り・欠損（フォールバック発動・空リスト返却等）。ユーザー影響が直接発生する |
| **診断ツール** | `audit.py`・`report_consistency_check.py`等、品質監視のみを目的とする経路 | 誤検知・検知漏れ（診断機能自体の機能不全）。直接のユーザー影響はないが、他の実害を隠蔽するリスクがある |
| **周辺ツール** | STONKS SILO・discover配下等、本流のパイプラインとは別に同一データソースを参照する経路 | 見落とされやすい（「本流だけ直せばよい」という思い込みが起きやすい） |

`[[TTM-PASCALCASE-KEY-STALE-1]]`では、この洗い出しが行われなかったため、
本番消費者（`data_fetcher.py`）・診断ツール（`audit.py`）の両方が同時に
取り残された。

### Step 2: 移行後 — 全消費者の動作確認

Step 1でリスト化した**全消費者**に対して、移行後に実際に想定通りの値を
返しているかを個別に確認する。

- 「参照先データファイルが存在する」「例外が発生せず実行が完了する」
  だけでは不十分。**値そのものが正しいか**まで確認すること。
- 特に以下のような**サイレントな異常**は、実行が正常終了するため見落としやすい:
  - `dict.get(key, {})`のようなデフォルト値付きアクセスが、キー不在時に
    静かに空dict/Noneを返し続けるケース
  - フォールバック機構（例: TTM系列→年次実績への後退）が、本来発動
    すべきでない状況で発動し、かつ`available=False`や`fallback`等の
    フラグ自体は「機能している」ように見えてしまうケース
  - 空リスト・空dictを起点にした後続処理が、件数0のまま正常終了するケース
- 確認方法の例: 移行前後で同一銘柄・同一日付の出力を実際に比較する
  （`git show HEAD:<path>`等で移行前の値を取得し、現在値と突合する）。
  出力全体の「変化なし」を確認するだけでなく、「本来変化すべき箇所が
  正しく変化しているか」も確認すること（`[[TTM-PASCALCASE-KEY-STALE-1]]`
  では、FCFソースが本来`ttm_series`であるべきところが`annual_fallback`の
  まま3日間変化していなかったことが、実害の実体だった）。

### Step 3: 旧パイプライン撤去前 — 横断的な旧キー参照の再確認

旧パイプライン（旧キー命名規則・旧スキーマ・旧ファイル）を撤去する**前**に、
旧キー名・旧フォーマットへの参照がリポジトリ全体に残っていないか、
Step 1と同様の手法でgrep等により**最終確認**する。

- この確認をパスするまで、旧パイプラインは削除しない。
- 「新パイプラインへの切替が完了した」ことと「旧パイプラインへの参照が
  ゼロになった」ことは別の事実であり、後者を確認せずに前者だけで
  旧パイプラインを削除すると、Step 1で洗い出したはずの消費者リストに
  漏れがあった場合に検知手段自体を失う。

## 実例（教訓）: フェーズC `ttm_series.json`キー移行（2026-07-25〜29）

`common/sec_data`統合フェーズCで、`ttm_calculator.py`の`flow`辞書キーを
PascalCase（`"Revenue"`/`"OCF"`/`"NetIncome"`等）からsnake_case
（`"revenue"`/`"operating_cash_flow"`/`"net_income"`等）へ移行する際、
上記Step 1（全消費者の洗い出し）が行われなかった。

**発生した実害**:
- コード変更コミット（2026-07-25 20:34 JST）自体には問題がなかったが、
  Phase C後最初の自動データ再生成（2026-07-26 21:50 JST）で
  `ttm_series.json`の実データがsnake_case化された時点から、以下2箇所が
  旧キー参照のまま取り残されていたことが顕在化した:
  - `common/sec_data/audit.py`（診断ツール）: NI/OCF/Revenueチェックが
    監視100銘柄**全件**で誤って「全件None」の重大エラーを報告
  - `src/value/tanuki_valuation/data_fetcher.py`（本番消費者）:
    `build_rice_annual_shape()`・`get_fcf_series()`が同一の旧キー
    （`"OCF"`/`"CapEx"`/`"Revenue"`/`"NetIncome"`等）を参照しており、
    **RICEスコアが監視100銘柄全件で完全停止**（`rice.available=False,
    note="SEC年次データ未取得"`という誤った表示）、**FCFソース選択が
    94銘柄で本来のTTM系列ではなく年次実績へ誤って後退**していた
- この状態が2026-07-29の発見・修正まで**約3日間**継続した
- DCF/Intrinsic Value自体は`_select_fcf_source()`側の既存フォールバック
  設計に救われ実害を免れていたが、これは偶然の設計上の非対称性（
  `get_fcf_series()`はフィルタ後の結果で判定していたため機能した一方、
  `build_rice_annual_shape()`の呼び出し元は生シリーズの非空判定だけで
  データソースを確定させていたため機能しなかった）によるものであり、
  本来はStep 1・2のチェックで発見・防止できたはずの障害だった

**教訓**: データ生成側（producer）のみを見て「移行完了」と判断せず、
本チェックリストのStep 1〜3を、生成側の変更と同一のタイミング・同一の
レビュー範囲で実施すること。特にStep 2の「実行が正常終了する」ことと
「値が正しい」ことの違いを常に意識すること（本件はいずれの消費者も
例外を送出せず正常終了していたため、実行ログだけでは異常に気づけなかった）。

詳細な調査経緯・修正内容は`BACKLOG_DONE.md::[[TTM-PASCALCASE-KEY-STALE-1]]`を参照。
