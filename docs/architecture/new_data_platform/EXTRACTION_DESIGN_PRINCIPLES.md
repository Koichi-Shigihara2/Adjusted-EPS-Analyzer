# EXTRACTION_DESIGN_PRINCIPLES.md — 新規データ層のための抽出設計原則

作成日: 2026-08-02
出発点: `common/sec_data/`抽出アーキテクチャの俯瞰的脆弱性分析（チャット記録）。
2026-08-01〜02セッションで発見した5つのバグ（[[PERIOD-LENGTH-VALIDATION-
GAP-1]]・[[TOTAL-LIABILITIES-FALLBACK-TAG-DESIGN-FLAW-1]]・[[PL-FIELD-
CROSS-ACCN-PERIOD-MISMATCH-1]]・[[SPAC-SHELL-BS-ENTITY-MIXING-1]]・
[[TTM-CALC-QUARTER-CONTIGUITY-UNCHECKED-1]]）は、個別には無関係に見えたが、
俯瞰すると共通の設計欠陥に帰着することが判明した実例を踏まえて作成する。

## 背景

`common/sec_data/`の値抽出関数群（`parser.py::_extract_single_key()`・
`_extract_values_best_candidate()`・`_collect_own_data_instant()`、
`layer3_builder.py::_merge_normalized_by_priority()`、
`ttm_calculator.py::calc_ttm_series()`等）は、いずれも「複数の候補
（XBRLタグ・accn・期間・四半期）から1つの値を確定する」という同じ形の
問題を解いている。この確定ロジックが、実際には**「最も新しいデータを
持つ候補」という単純な基準だけで独立に値を確定させ、以下3種の妥当性の
いずれも検証していなかった**ことが、5バグに共通する根本原因だった:

1. **期間の妥当性**: 採用しようとしている値が、本来想定される期間の長さ・
   時系列としての連続性を満たしているか
2. **フィールド間整合性**: 相互に関連する複数のフィールドが、同一の
   ソース・同一の期間から一貫して取得されているか
3. **既知の制約・恒等式との整合性**: ドメイン上必ず成り立つはずの関係
   （会計恒等式等）に違反していないか

`common/sec_data/`は既に本番稼働中で構造自体を作り直すコストが高いため、
個別バグへの対処（ゲート条件の追加）を積み重ねる形で対応してきた
（詳細は`BACKLOG.md`/`BACKLOG_DONE.md`の該当エントリ、および
[[ACCOUNTING-IDENTITY-VALIDATION-LAYER-MISSING-1]]・[[CHECK29-
ACCOUNTING-IDENTITY-DETECTION-LAYER-1]]参照）。本ドキュメントは、この
教訓を**これから新設する`common/market_data/`・`common/macro_data/`**
（`PROJECT_STATUS.md`フェーズ1、2026-08-02時点で未着手）の設計に、
最初から組み込むことを目的とする。

## 本ドキュメントの位置づけ

- **本ドキュメント**: 新規データ層の抽出・選定ロジックが最初から満たす
  べき**設計原則**を記録する（「同種の設計欠陥をどう予防するか」）。
- `MIGRATION_CHECKLIST.md`: スキーマ移行時の消費者横展開手順を記録する
  （「移行時に何を確認すべきか」）。本ドキュメントとは対象タイミングが
  異なる（本ドキュメントは新規設計時、`MIGRATION_CHECKLIST.md`は既存
  データのスキーマ変更時）が、いずれも実際のインシデントから汎化した
  「手順・原則」文書という点で同型。
- `BACKLOG.md`/`BACKLOG_DONE.md`: 個別の課題・完了記録（「何が起きたか」）。
- `SEC_EDGAR_LAYER_DESIGN.md`: SEC EDGARレイヤー統合固有の設計判断
  （「なぜこの設計にしたか」）。

既存ファイルの記述は変更しない。

## 適用範囲

**本ドキュメントは、これから新設する`common/market_data/`・
`common/macro_data/`等の新規データ層への適用を主目的とする。**

`common/sec_data/`自体への遡及適用（既存の抽出関数群の構造変更）は
本ドキュメントの範囲外である。[[ACCOUNTING-IDENTITY-VALIDATION-LAYER-
MISSING-1]]（俯瞰分析の予備スキャンで見つかった未分類の違反・156件の

結果と、[[CHECK29-ACCOUNTING-IDENTITY-DETECTION-LAYER-1]]（横断的検証
レイヤーの新設提案）の実装可否判断を踏まえて、`common/sec_data/`への
適用要否は別途判断する。

## 新規データ層が満たすべき3原則

### 原則1: 候補選定は「新しさ」だけでなく期間・時系列の妥当性を検証すること

値を複数候補（同一概念の異なるタグ・異なる期間・異なる時点のスナップ
ショット等）から選定する際、単一の「最も新しい」基準だけで確定せず、
その候補が**本来想定される期間の長さ・時系列としての連続性**を満たして
いるかを必ず検証すること。

- 教訓1（[[PERIOD-LENGTH-VALIDATION-GAP-1]]）: 年次値を選ぶ際に、対象
  期間の日数を検証しなかったため、91日程度の四半期実績が年次値として
  誤採用されていた。
- 教訓2（[[TTM-CALC-QUARTER-CONTIGUITY-UNCHECKED-1]]）: 直近4件という
  「件数」だけを見て trailing-window を構成し、実際にその4件が連続した
  期間を覆っているかを検証しなかったため、2年以上離れた期間の値が
  「トレーリング12ヶ月」として黙って再利用されていた。

新規データ層（市場データの日次/週次系列、マクロ指標の時系列等）でも、
「直近N件」「最新の値」という選定ロジックを実装する箇所では、件数だけ
でなく期間・日付の連続性を検証する設計を最初から組み込むこと。

### 原則2: 相互に関連するフィールドは独立に抽出・選定しないこと

相互に関連するフィールド（同一概念の異なる表現、または計算上関連する
フィールド群）は、独立に抽出・選定せず、**同一のソース・同一の期間から
の取得を優先するか、明示的な整合性チェックを経ること**。

- 教訓1（[[PL-FIELD-CROSS-ACCN-PERIOD-MISMATCH-1]]）: `revenue`・
  `cost_of_revenue`・`gross_profit`という相互に関連するフィールドが、
  それぞれ独立に「最も新しいaccn（提出書類）」を選んでいたため、異なる
  会計年度・異なる提出書類のデータが混在していた。
- 教訓2（[[SPAC-SHELL-BS-ENTITY-MIXING-1]]）: 貸借対照表の複数フィールド
  が、独立に「最も新しいaccn」を選んでいたため、SPAC合併等で法的実体が
  変わった際に、異なる法人のデータが同一年度のBSとして混在していた。

新規データ層でも、複数の関連指標を別々のAPI呼び出し・別々の抽出ロジック
で取得する設計を採る場合、後段で「同一の基準時点・同一のソースから
取得されているか」を突き合わせる仕組みを持つこと。取得元が単一API・
単一レスポンスに閉じる場合はこの限りではないが、複数ソースを組み合わせる
設計では特に注意すること。

### 原則3: ドメイン固有の既知の制約・恒等式を、抽出後・保存前に検証する仕組みを最初から組み込むこと

ドメイン上必ず成り立つはずの制約・恒等式（会計恒等式に限らない）を、
**抽出後・保存前に検証する仕組みを、新設計の初期段階から組み込むこと**。
事後的に個別バグ発見のたびに個別ゲートを追加するのではなく、横断的な
検証レイヤーとして最初から設計すること。

- 教訓（[[TOTAL-LIABILITIES-FALLBACK-TAG-DESIGN-FLAW-1]]）: 候補タグの
  1つが「定義上、他のフィールドと必ず一致してしまう」誤ったタグだった
  ため、`total_liabilities == total_assets`という明白な自己矛盾を持つ
  値が105銘柄中278件で採用され続けていた。この種の矛盾は、恒等式検証が
  存在すれば候補タグ追加の時点で即座に検知できたはずだった。
- 教訓（[[CHECK29-ACCOUNTING-IDENTITY-DETECTION-LAYER-1]]）: `common/
  sec_data/`には`_bs_math_violations()`という恒等式検証ロジックが存在
  するが、これは特定バグ（SPAC-SHELL-BS-ENTITY-MIXING-1）の発火条件
  としてのみ事後的に作られた狭いゲートであり、汎用的な検証レイヤーとして
  設計されたものではない。

新規データ層のドメインで検証可能な制約の例:
- 市場データ（`common/market_data/`）: 価格・出来高等が0以下にならない、
  高値≥安値、52週高値≥52週安値、時価総額=株価×発行済株式数の近似一致等
- マクロ指標（`common/macro_data/`）: 比率指標が定義域（例: 失業率0〜
  100%）を外れない、季節調整値と非季節調整値の乖離が異常に大きくない、
  同一系列の値が前月から桁違いに変化していない等

これらは新規データ層の設計・実装と**同時に**（後から追加するのではなく）
組み込むこと。

## チェックリスト: 新規データ層着手時に確認すべき質問

`common/market_data/`・`common/macro_data/`等、新規データ層の設計・
実装に着手する際は、以下を確認すること。

- [ ] このフィールドの値を複数候補（複数API・複数エンドポイント・複数
      時点のスナップショット等）から選定する場合、「最新のもの」以外の
      基準（期間の長さ・時系列の連続性）を検証しているか（原則1）
- [ ] 「直近N件」という選定ロジックがある場合、そのN件が実際に連続した
      期間を覆っているか（隙間なく並んでいるか）を検証しているか、
      それとも件数だけをチェックしているか（原則1）
- [ ] 相互に関連するフィールド（例: 高値・安値・終値、または複数の
      マクロ指標間の定義上の関係）は、同一のソース・同一の基準時点から
      取得しているか。複数ソースを組み合わせる場合、突き合わせの仕組みが
      あるか（原則2）
- [ ] このドメインで既知の制約・恒等式（価格>0、比率の定義域、指標間の
      算術的関係等）を洗い出したか。それらを抽出後・保存前に検証する
      仕組みがあるか（原則3）
- [ ] 上記の検証は、個別のバグ修正のたびに後付けで追加する設計になって
      いないか。設計の初期段階から、検証結果を記録するログ・レポートの
      仕組み（既存の`fy_collision_log.json`・`spac_shell_detection_
      log.json`等と同種の「0件でも毎回書き込む」パターン）を組み込んで
      いるか（原則3）
- [ ] 候補選定・整合性検証のロジックを変更した場合、`MIGRATION_
      CHECKLIST.md`のStep 1〜3（全消費者の洗い出し・移行後の動作確認・
      旧参照の最終確認）を実施しているか
